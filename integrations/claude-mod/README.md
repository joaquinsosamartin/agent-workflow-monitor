# Claude Code Mod — Agent Workflow Monitor (first iteration)

This is a **real Claude Code Mod plugin**, not a classic shell hook. It provides:

- `/workflow` to open a native Claude Code pane.
- Current main-turn status and context-window occupancy.
- Subagent inventory from `$.agent.list()` (name, status, model where exposed).
- Last twelve tool names with local time and the agent identifier.
- Manual refresh and close controls.

It observes Claude without changing prompts, tool permissions, or tool execution. It intentionally does not store prompts, tool arguments, outputs, or secrets.

## Requirements

Claude Code **2.1.287+** with Mods enabled (CLI or Desktop Code view). The API is evolving, so you must validate the plugin against your exact installed version.

## Windows PowerShell

From the repository root:

```powershell
claude --version
claude plugin validate .\integrations\claude-mod
claude --plugin-dir .\integrations\claude-mod
```

Within the new Claude Code session, execute `/workflow` to open the pane.

If you get a `ui.render` validation error, run `claude --debug --plugin-dir .\integrations\claude-mod`; inspect `integrations/claude-mod/.claude-plugin/types/` generated by that version and adjust the `Pane` render-site props. Do not run this plugin in an unattended sensitive environment until the hooks have been reviewed.

### Current limitations

- The UI reads only the Claude Code **session** and subagents of the Claude instance where it is installed.
- It does not infer cross-process Codex → Claude orchestration by time or directory name.
- Context tokens are **not** billable token usage; dollar costs are not fabricated.
- **Local bridge now implemented (v0.2)**: the Mod attempts to send Claude session status, named subagents and the last tool name to `http://127.0.0.1:8765/api/integrations/claude/events` using the host-mediated `$.http.fetch`. It shares session IDs with the JSONL observer to avoid duplicate runs.
- The bridge is best-effort: if the local backend is stopped or Claude policy refuses loopback network access, the native panel continues functioning, and its “Monitor local” row shows why.
- Tokens shown as `Contexto` are **context-window occupancy**, not billable token usage. No guessed USD costs are sent or saved by the Mod. Existing JSONL usage stays the source for token counters.
- A full vertical phase/step plan and task-level costs will require stronger workflow events than Claude's raw tool call stream.
- Pane docking depends on Claude Code surface and terminal width.

Documentation: https://code.claude.com/docs/en/plugins/mods/create

No GitHub Actions are used.

## Run the local backend and Claude Mod together (Windows)

Start Agent Workflow Monitor in one PowerShell terminal:

```powershell
cd C:\git\agent-workflow-monitor
git pull
.\.venv\Scripts\python.exe -m monitor serve
```

In another PowerShell window:

```powershell
cd C:\git\agent-workflow-monitor
claude plugin validate .\integrations\claude-mod
claude --plugin-dir .\integrations\claude-mod
```

Inside Claude Code, run `/workflow` and then ask Claude to execute a small task. When the turn finishes, the Mod will attempt to synchronize the session and any named subagents. The pane displays `Monitor local: conectado` if the request succeeds.

The endpoint is local-only and requires the same `X-Monitor-Key` used by other Agent Monitor APIs. The Mod retrieves the key via the localhost bootstrap route and does **not** include prompts, tool arguments, tool outputs or transcript bodies in its payload. Only use this plugin with a local monitor instance you trust.

### Diagnostics

- Monitor status: `http://127.0.0.1:8765/api/health`
- Claude Mod ingestion endpoint: `POST /api/integrations/claude/events`
- Open the web UI and expand **Historial de sesiones** to inspect a Mod-synchronized run. If the Claude process has no verified PID-to-session correlation, it may not appear within the process-only tree.
- If the pane says `Monitor local: no disponible`, inspect its error text and Claude's debug output. Some installations may restrict `$.http.fetch` to loopback or disable it by policy.
- The Mod requires a new Claude process after changes to its source unless your installation supports hot reload.

Run local Python tests:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

No GitHub Actions have been configured or run for this feature.

## Provider-neutral vertical workflow (shared plans)

The Mod can now query `GET /api/workflows` and display a selected
plan's steps as an expandable vertical-style list with child steps,
statuses and **provider/agent labels**. The plan itself is not owned by
Claude: one phase may be executed by Codex, another by Claude, and another
by Orca. Handoffs keep the phase identifier stable.

Create the sample plan with the PowerShell commands in the repository
README, restart the Python server to load the new API, then restart Claude
Code and run `/workflow`. Choose a plan with the **Ver** button;
expand a phase with `+`. Claude's own subagents and tool activity remain
in a separate section.

This view is currently **read-only**. Plan-state changes require explicit
authenticated events from an agent integration; parsing arbitrary tool
operations is not a reliable way to determine a phase's completion.
The terminal Mod cannot use HTML/CSS from the web dashboard, so its stepper
is rendered using native terminal components. No GitHub Actions.

## Shared Codex subagent view

The native Claude Code Mod now has a **CODEX · ORQUESTACIÓN COMPARTIDA**
section in addition to its Claude-only subagent list. This section reads
the selected Codex orchestrator and thread-based subagent hierarchy from
the shared FastAPI dashboard. It is entirely **read-only**: it does not
invoke Codex, manage Codex processes or infer that Codex subagents are
Claude agents.

Select the principal **Codex PID** and its **root Codex session** in the
web dashboard first. Then, when the Claude Mod is open, press
**Actualizar**. The Mod displays nested Codex threads with expandable
children, observed lifecycle and verified token/cost totals when the
corresponding JSONL exists. Missing sessions and unavailable cost data
are marked as such.

**This does not require Claude Code to be running for Codex monitoring**:
the normal web dashboard is the Codex view, and the Claude Mod is only a
secondary shared view if you happen to use Claude Code. A standalone
native Codex panel/extension remains planned rather than implemented.
